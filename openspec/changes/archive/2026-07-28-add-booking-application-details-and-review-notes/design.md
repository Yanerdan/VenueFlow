## Context

Booking 当前只持久化用户、时段、人数和状态，创建请求的幂等哈希也只覆盖这些字段。审批动作没有请求体，前端只能在列表中执行状态按钮。C27 需要在不改变既有容量与可靠性协议的情况下，让 Booking 成为申请内容和审批结论的事实源。

## Goals / Non-Goals

**Goals:**

- 以向后兼容迁移保存申请内容和最新审批结论。
- 让创建幂等哈希覆盖新增申请字段。
- 让审批、驳回和取消接受有界意见，并在 DTO 中返回。
- 在申请人端和管理端提供可读详情体验。

**Non-Goals:**

- 不实现附件、富文本、多级审批模板、会签或完整审计报表。
- 不改变 Resource 容量接口、User 资格接口和 Outbox 事件结构。
- 不增加新服务或前端构建依赖。

## Decisions

1. **使用 Booking V006 增量列。** 在 `booking_reservation` 增加活动名称、用途、联系人、联系电话、备注、处理意见、处理人角色和处理时间；既有记录保持可读，缺失详情明确显示为历史申请。
2. **创建字段参与幂等哈希。** 同一幂等键若申请内容不同必须冲突，防止用户修改备注后错误重放旧申请。
3. **使用统一动作请求 DTO。** 确认、取消和驳回复用有界 `reviewNote`；新增显式 rejection 动作，内部仍转换到 `CANCELLED`，但持久化驳回原因供界面区分。
4. **只保存最新处理结论。** 当前阶段不新增独立审批历史表；既有 `booking_status_log` 继续记录状态转移，预约行保存最新人类可读意见。
5. **前端使用详情面板而非新路由。** 零构建应用在现有列表上展开详情，减少导航和状态管理成本。

## Risks / Trade-offs

- [只保存最新意见不能形成完整会签历史] → 当前状态日志保留状态审计，完整审批链留给后续多级审批 change。
- [历史申请缺少业务字段] → DTO 允许可空并在界面显示“历史申请 / 待完善”，不伪造内容。
- [新增字段扩大幂等哈希] → 仅新请求使用新标准化格式，已成功记录仍按持久化结果重放。

## Migration Plan

1. 停止 Booking 后执行 V006，新增列全部允许既有记录兼容。
2. 发布扩展后的领域模型、创建 DTO、动作 DTO 和查询 DTO。
3. 发布申请人端完整表单与管理端详情面板。
4. 回滚应用时保留 V006 列，不修改既有迁移。
