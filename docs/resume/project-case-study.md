# VenueFlow 项目案例

## 一句话定位

VenueFlow 是一个面向高校部委、学院和职能部门的校园资源预约与审批治理平台，通过微服务、可靠事件和组织权限模型完成资源从发布到核销的全流程管理。

## 为什么值得作为工程作品

普通预约系统容易停留在表单和状态字段。VenueFlow 选择了四个更接近真实业务的难点：

1. 浏览器重试、网络超时和并发提交下，容量不能超卖。
2. 审批责任随资源和组织变化，但历史流程必须可审计。
3. 通知与搜索可以延迟，却不能拖垮核心交易。
4. 登录身份、人员组织和业务权限必须分层治理。

## 我的工作范围

这是个人全栈工程作品，覆盖需求规格、领域拆分、后端实现、浏览器双工作台、数据库迁移、消息链路、本地基础设施、自动化验收和工程文档。仓库采用 OpenSpec 保存逐步变更的提案、设计、任务和归档，便于说明系统如何演进，而非只展示最终代码。

## 关键决策

### 按业务一致性边界拆分服务

身份、人员、资源、预约、通知和搜索分别拥有自己的状态；Gateway 只负责入口治理。拆分标准不是“一个表一个服务”，而是哪组不变量需要在同一事务中成立。

### 用台账与补偿保护容量

Resource 服务拥有容量事实，Booking 服务拥有流程事实。跨服务操作使用幂等请求、预占令牌、超时释放和对账补偿处理未知结果，而不是依赖脆弱的分布式事务。

### 用 Outbox 解耦派生能力

预约与事件在同一事务落库，通知和搜索异步消费并去重。这样即使消息系统或 Elasticsearch 短暂不可用，预约交易仍可完成，派生视图可恢复。

### 用审批快照保证历史语义

资源支持 1–5 级有序审批。提交申请时复制策略为审批步骤快照，避免配置变化反向改变进行中或已结束流程。

### 用 OIDC 与组织同步连接校园治理

Auth 实现 Authorization Code + PKCE，User 支持组织树全量/增量同步。认证只回答“你是谁”，组织与角色授权回答“你能做什么”。

## 可复核成果

- 7 个可独立启动的后端进程和申请人/管理端两个浏览器工作区。
- 39 份主规格、28 个数据库迁移、完整的本地启停与冒烟链路。
- 当前本地 Surefire 报告为 277 项测试且无失败；前端 19 项测试通过。
- 合成运营数据覆盖组织、人员、资源、排期、预约、审批、通知与报表。

## 诚实边界

项目可用于完整演示和技术面试，但没有声称已在真实学校生产运行。真实落地仍需完成目标学校的 IdP/组织源联调、安全审计、容量压测、灾备演练和用户试用。这一边界本身也是工程判断的一部分。
