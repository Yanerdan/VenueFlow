## Context

VenueFlow 已有七个可独立运行的服务、统一 Gateway、可靠预约生命周期和一个零构建用户端。当前差距主要在产品组织方式：令牌没有角色、预约只能按用户查询、确认和签到暴露给普通用户，也没有将现有资源写接口组织为学校管理工作台。

## Goals / Non-Goals

**Goals:**

- 在不增加微服务的前提下形成申请人端和学校管理端双工作区。
- 用少量向后兼容改动打通角色、审批、资源维护和运营概览。
- 保持零构建前端与现有服务边界，确保本地环境可快速演示。

**Non-Goals:**

- 不实现学校统一身份认证、组织目录同步和细粒度权限配置。
- 不实现可配置多级审批流、委托审批、冲突规则引擎和报表导出。
- 不覆盖生产安全加固、压测、真实试用与发布交付材料。

## Decisions

1. **角色由 Auth 持久化并进入 JWT。** 凭证增加 `role` 列，注册默认 `APPLICANT`；本地管理员通过脚本提升。相比新建 IAM 服务，这能以最小变更形成可信角色来源。
2. **Gateway 继续作为信任边界。** 它删除客户端伪造的身份头，从已验证 JWT 写入 `X-User-Id` 与 `X-Role`。管理 API 只接受 Gateway 传递的受支持管理角色。
3. **审批复用现有预约状态机。** `PENDING_CONFIRMATION` 表示待学校审批，确认表示通过，取消表示撤回或驳回，签到表示核销。不新增审批微服务和状态表。
4. **管理查询留在 Booking Service。** 新增有界的全局预约分页查询；统计在浏览器端对资源和预约结果做轻量聚合，避免为了首页数字建立聚合服务。
5. **管理前端与用户端共享零依赖 API 客户端。** `admin.html` 和独立 ES module 提供工作台、审批、资源和时段管理；保持静态服务器即可运行。

## Risks / Trade-offs

- [单角色模型不能表达复杂学校组织] → 本阶段固定五类角色，并为后续组织与策略服务保留扩展点。
- [取消同时承担用户撤回与管理员驳回] → 界面按操作者显示不同文案，审计仍由既有状态日志保留。
- [前端聚合统计只覆盖有界查询结果] → 明确标注为当前运营概览，后续再增加专用统计查询。
- [直连下游端口可绕过 Gateway 角色头] → 本地演示统一经 Gateway；生产网络隔离与服务间鉴权列入后续安全建设。

## Migration Plan

1. Auth 先执行向后兼容的 V002 迁移，既有凭证自动成为 `APPLICANT`。
2. 发布 Auth 和 Gateway，使新令牌开始携带和传播角色；旧令牌仍可被识别为申请人。
3. 发布 Booking 管理查询和角色校验，再部署双工作区前端。
4. 本地种子脚本创建或提升演示管理员；回滚时前端退回用户端，新增角色列可安全保留。
