## Context

User Service 当前只保存外部身份、显示名称和资格状态，管理审批只能看到 Booking 的内部用户 ID。C25 已提供可信角色和管理工作台，因此可在不改变 Booking 所有权的前提下，由前端通过 User 管理查询补全人员展示。

## Goals / Non-Goals

**Goals:**

- 建立向后兼容的校园身份资料与本人维护能力。
- 提供有界的人员目录，让审批和人员管理使用可读身份。
- 保持 User 为资料唯一事实源，Booking 继续只保存用户 ID。

**Non-Goals:**

- 不接入真实学工系统、统一身份认证或组织同步。
- 不实现组织树、批量导入、数据脱敏策略和复杂人员授权。

## Decisions

1. **使用 User V002 增量列。** 增加可空学工号、人员类型、院系、电话和邮箱；既有行自动使用 `OTHER` 人员类型并可逐步补全。
2. **本人资料采用版本化 PATCH。** 复用既有乐观锁版本，避免引入另一份资料表。
3. **人员目录由 User 提供有界分页。** 支持姓名、学工号和院系关键词；仅审批人员和系统管理员可访问。
4. **审批页面在浏览器端有界关联。** 管理端并行读取最多 100 条预约和人员资料，以用户 ID 关联显示；不让 Booking 跨服务读取或复制 User 数据。

## Risks / Trade-offs

- [管理端关联只覆盖当前有界页] → 当前演示数据量足够，后续报表服务再做服务端聚合。
- [自填学工号不能证明真实身份] → 标注为本地产品流程，正式接入时由校园身份源覆盖。
- [既有用户资料不完整] → UI 明确显示“待完善”，本人可随时补全。

## Migration Plan

1. User 执行 V002，保持既有行可读。
2. 发布扩展 DTO、本人更新与管理查询。
3. 发布申请人资料中心和管理端人员目录。
4. 回滚前端和接口时保留新增列，不修改 V001/V002。
