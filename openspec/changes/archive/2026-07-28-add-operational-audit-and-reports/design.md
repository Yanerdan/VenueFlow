## Context

Booking Service 已持久化预约状态、人数、资源 ID、归属部门、指定审批人、审批决定和处理时间。管理端目前只能加载预约列表并在浏览器内计算少量指标，既缺乏全量聚合，也没有清晰的审批审计视图。

## Goals / Non-Goals

**Goals:**

- 通过一个只读 API 返回管理首页所需的全部运营汇总。
- `SYSTEM_ADMIN` 查看全局数据，`APPROVER` 只查看分配给自己的数据。
- 使用数据库聚合，避免将全部预约加载到浏览器。
- 用现有零构建前端展示可直接验收的管理报表。

**Non-Goals:**

- 不建设数据仓库、BI 平台或异步统计流水线。
- 不提供 CSV/PDF 导出、任意日期范围和复杂自定义维度。
- 不跨服务复制资源名称；前端使用已加载的资源目录映射资源 ID。
- 不替代生产级不可篡改审计日志。

## Decisions

1. 新增 `GET /api/v1/bookings/management/report`，一次返回指标、资源统计、部门统计和最近审批记录。相比多个小接口，这能减少管理首页请求与前端状态管理。
2. 聚合直接查询 `booking_reservation`。该表已有业务快照，足以支持当前演示规模；不新增表或迁移。
3. 统计范围沿用审批权限：系统管理员不加范围条件，普通审批人按可信 `X-User-Id` 匹配 `assigned_approver_external_user_id`。
4. 通过率以已作出审批决定的申请为分母，以 `APPROVED` 为分子；没有审批决定时返回 0。
5. 最近审计记录使用预约号、决定、角色、意见和处理时间，按处理时间倒序限制 20 条。

## Risks / Trade-offs

- [直接聚合会随数据量增长变慢] → 当前阶段保持简单，查询使用已有状态、审批人和创建时间索引；规模增长后再建设预聚合。
- [历史预约可能没有资源或部门快照] → 统一归入“未归属”，资源 ID 为空时不进入资源排行。
- [前端资源名称依赖资源目录] → 映射失败时明确显示资源编号，保证报表仍可用。
